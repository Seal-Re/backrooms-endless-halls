# 后室文字游戏 调研与设计建议

> 目标：在 Windows 本机制作一款"后室"题材的文字游戏 / 对话小说（IF），要求**单文件可双击运行**、含**状态 / 物品 / 分支 / 多结局**。
> 本文档基于四份调研要点（现有后室游戏全景、后室文字/IF 先例、IF 引擎对比、生存恐怖 IF 机制设计）综合而成，并对接本仓库已有的后室知识库（`后室/层级`、`后室/实体`、`后室/物品`、`后室/组织`）。
> 编写日期：2026-06-13

---

## 0. 一句话结论（给赶时间的读者）

- **首选技术方案：Twine（SugarCube 2 格式）+ "Publish to File" 导出自包含单 HTML**。它原生满足"双击即玩 / 状态机 / 库存 / 存档 / 多结局 / 中文 UTF-8"，是后室"层级探索 + 物品 + 理智 + 逃脱"题材的最短路径。
- **核心玩法循环固定为后室三件套**：**Sanity（理智，隐藏数值）+ 杏仁水（多变体消耗品）+ 实体规避**。理智越低，叙事越不可靠（借 NoClip）。
- **氛围核心是"存在性孤独"而非 jumpscare**：缓慢累积的 dread > 频繁惊吓。`The Backrooms 1998` 因"过量 jumpscare 稀释氛围"被反复差评，是最大反面教材。
- **叙事结构主干用 Branch-and-Bottleneck + Quest 混合**：每"层级"= 一个汇合点（bottleneck），层内按地理探索（quest 模块），安全房间放存档点。

## 1. 现有后室游戏的可借鉴点与"纯文字化"取舍

### 1.1 现有游戏全景（两大类）

| 类别 | 代表作（口碑） | 核心机制 | 好评点 | 差评点 |
|---|---|---|---|---|
| **协作解谜逃脱** | Escape the Backrooms（89%/约4万评）、Backrooms: Escape Together（89%/约1.3万）、Inside the Backrooms、Apeirophobia（免费，3.8亿访问） | 1–4 人合作、proximity 语音（实体可听见你→需噤声）、库存/资源管理、按层切换的谜题、各具机制的实体（如 Skinwalker 假扮被杀队友）、程序生成保证"每次跑图不同" | 氛围（无配乐、只有荧光灯嗡鸣）、迷路恐慌、panic 在队伍里传染 | 配对 bug、程序生成有时无聊 / 难度尖峰 |
| **纯氛围步行模拟** | POOLS（95%/3255评）、The Complex: Found Footage（87%）、The Backrooms 1998 | 无怪物无战斗，靠空间感知、声场、"是否真的独自一人"的疑虑制造 dread | 极致 liminal 孤独感、留白 | **1998 因过量 jumpscare 稀释氛围被反复差评** |

### 1.2 核心恐怖来源（来自 GameDeveloper / SlashFilm 分析）

恐惧**不在"会受什么伤"，而在"孤身处于此地的孤独"**。四个支柱：

1. **uncanny familiar**：熟悉却错位的办公室 / 泳池。
2. **getting lost**：每转一个弯就磨损你的方向感与现实感。
3. **留白 > 明示**：`Exit 8` 用极少元素达成最大恐怖。
4. **循环 + 微小漂移**：回到熟悉场景但加不可名状的小变化，瓦解方向感。

### 1.3 → 纯文字化的取舍（哪些机制天然适配文字 / 哪些必须舍弃或转译）

| 原 3D 机制 | 文字化处理 | 取舍判断 |
|---|---|---|
| 第一/第三人称空间感 | **第二人称现在时**（"你站在…"）——IF 标准，强迫读者代入被困者 | ✅ 强化保留 |
| 孤独感（声场/空房间） | 用文字**精确点名"缺席"**：描述空房间、无人的回声、本应有人的地方没有人 | ✅ 文字优势，重点放大 |
| 程序生成跑图 | 转译为**可变叙事段落 / 静态层 + 随机节点**（roguelike 思路），提升重玩性 | ✅ 转译保留 |
| 实体本体的视觉呈现 | **不描述实体本体**——文字最擅长"未知不可见"；只写痕迹、声音、错位 | ✅ 文字优势 |
| proximity 噤声机制 | 化为**文字选择 + 计时压力**（"屏住呼吸 / 保持静止" 选项，错选惊动实体） | ✅ 转译保留 |
| 资源/库存管理 | 杏仁水 / sanity / 电量等做成**显式或隐藏状态变量** | ✅ 保留 |
| jumpscare 突袭恐吓 | **严控**，主打缓慢累积的存在性焦虑 | ⚠️ 大幅削减（1998 教训） |
| 多人合作 / proximity 语音 | 单机文字难以复刻"panic 传染"；**舍弃多人**，或以 NPC 同伴的可靠性焦虑代偿 | ❌ 舍弃多人，转译为同伴信任机制 |
| 实时操作 / 反应类谜题 | 文字不适合实时；改为**限时选择 / 回合计数压力** | ⚠️ 转译为回合制压力 |

**纯文字化写作要点（落地为文风规范）**：
- 第二人称现在时贯穿全篇。
- **"先平庸后错位"**：先写日常细节（隔间、咖啡机、嗡鸣的灯），再插入一个不可能的元素（多出来的一道门、地毯花纹变了）。
- **感官极简**：荧光灯嗡鸣、白噪、寂静 > 视觉奇观。
- **循环描写**：让玩家回到"熟悉"场景但埋微小漂移，制造迷路与现实瓦解。

## 2. 已有后室文字 / IF 先例总结

### 2.1 三大形态及代表作

| 形态 | 代表作 | 技术 / 规模 | 评价 |
|---|---|---|---|
| **纯分支选项（CYOA）** | Bixbyte《Backrooms: Choices》(Python, 8结局, 几分钟, 重氛围无存活系统, itch.io)；Norbez《Romance the Backrooms》(Twine 约会 VN, 4.8★) | 轻量 | 《Choices》氛围强但极短；《Romance》被批"**选择影响小、互动少、恋爱玩法在 demo 里几乎缺席**" |
| **打字指令 + 状态栏的存活流** | lemonlemon《The Backrooms Text Game》(stamina/饥饿/血量状态条, 进房触发 7 类随机事件如停电/尸体/Deathmoth, 可拾取/招募 NPC, 目标=活更久/逃出 L0)；perrydeng《Backrooms.Survive》(forward/left/i/pick up/read/unlock 指令, 标注 objects ?/P/R/D, 明确"未用 AI") | 中量 | 普遍"**潜力大却 bug 多**"——道具/NPC 交互坏，反馈不清 |
| **AI 驱动 freeform** | NoClip(minnerlabs, 主打"理智下降→叙述者不可靠、18 层 wiki lore、无脚本每局不同")；AI Dungeon "College Backrooms"；character.ai "Backrooms Text Adventure"(仅 180 次互动) | 体量两极 | AI 带来不可靠叙事张力，但**缺死亡 / 资源后果与结构** |

### 2.2 共性发现（强玩家认知锚点）

- 存活机制普遍围绕 **Sanity 理智 + Almond Water 杏仁水（后室通用符号）+ 实体规避**。这是后室玩家的强认知锚点，**不要发明新符号去替代它们**。
- 数值手感参考：3D《Escape the Backrooms》把 sanity 做成**每 5 秒掉，杏仁水恢复约 50%**——可借鉴回合制下的"每回合掉理智 / 杏仁水回 50%"。

### 2.3 做得好 vs 做得差（直接转为本项目的"做 / 不做"清单）

**做得好（学习）**：氛围 / liminal 孤独感；杏仁水 / 分级 lore 的强 IP 辨识度；AI 带来的不可靠叙事张力；可访问性（色盲 / 字幕）。

**做得差（规避）**：
- 手写分支选择影响力弱 → **每个选择必须有可见后果**。
- 内容短 → **保证内容长度与多结局重玩性**。
- 存活系统常有 bug 且反馈不清 → **机制要简单可测、反馈清晰**。
- AI 版缺死亡 / 资源后果与结构 → **若用 LLM，必须配世界圣经（分级 wiki lore）约束防漂移 + 硬性死亡/资源规则**。

### 2.4 → 对本项目的启示（凝练）

1. 选"**打字指令 + 轻状态栏（理智/物资）**"或"**分支选项 + 隐藏状态**"混合，比纯 CYOA 更有后室味。
2. 把 **Sanity + 杏仁水 + 实体三件套**作为核心循环；理智低时触发不可靠叙事（借 NoClip）。
3. 必须做**存活 / 死亡后果与多结局**保证重玩。
4. 规避同类通病：选择要有真实后果、交互别留 bug、内容长度要够。
5. 若用 LLM 生成，需用**世界圣经（分级 wiki lore）**约束防漂移——本仓库 `后室/` 知识库正可充当世界圣经。

## 3. 引擎 / 技术方案对比表

> 评估维度：产物形态、中文支持、上手难度、可分发性（针对 Windows 本机、单文件可双击、含状态/物品/分支/多结局的需求）。

| 引擎 | 产物形态 | 单文件双击? | 中文支持 | 上手 | 状态/物品/分支/多结局 | 可分发性 | 适配度 |
|---|---|---|---|---|---|---|---|
| **Twine（SugarCube 2）** ★首选 | "Publish to File"导出**自包含单 HTML** | ✅ 双击即玩、无需服务器（图片/音频外链需随附，可内嵌 base64 保单文件） | ✅ UTF-8 直接写中文无碍；中文社区成熟（B站/小土刀/CSDN 教程多） | 中等 | ✅ 内置变量/setter、库存、存档、条件分支，**最适合带状态机的后室探索** | 极好（单 HTML） | ★★★★★ |
| **Ink + Inky（+ inkjs）** ★次选 | Inky 导出 JSON；用 **inkjs 把 JSON 内嵌进 HTML** 成真正单文件离线运行（避开本地 fetch 的 CORS） | ✅（需自己搭壳） | ✅ OK | 较高 | ✅ 叙事语法极强（线/编织/胶水/变量/函数）；但**物品 UI 要手写** | 好（内嵌后单 HTML） | ★★★★ |
| **纯手写单文件 HTML + JS** ★机动 | 天然单文件 | ✅ 天然双击运行 | ✅ 随意 | 低~中（取决于自造量） | 全自造（量大易乱） | 极好（零依赖） | ★★★（demo / 独特交互时） |
| **Python CLI 文字冒险** | 终端程序，**非单文件**（需 Python 或 PyInstaller 打 exe） | ❌（exe 体积大、观感差） | ✅ | 最低（逻辑最自由） | 自由实现 | 差（需运行时/打包） | ★★（仅原型） |
| **Ren'Py** | zip / 文件夹（数十~上百 MB exe 包） | ❌ 非单 HTML，偏重美术 | ✅ 原生中文 + 强逻辑 | 中 | ✅ 强 | 中（包大、偏重） | ★★（文字游戏过重） |
| **ChoiceScript** | 可导出 HTML，**但本地 Chrome 因外部脚本限制难直接运行**，需上传/特殊处理 | ❌ | ✅ | 中 | 范式偏统计选择 | 差（绑 Choice of Games 生态） | ★（不适合自由分发的单文件后室） |

**排序推荐**：Twine(SugarCube) > Ink+inkjs(内嵌单文件) > 纯手写 HTML > Ren'Py > Python CLI > ChoiceScript。

**明确推荐**：
> 后室的"**层级探索 + 物品/SAN/逃脱条件 + 多结局**" = **状态机 + 分支**，正中 SugarCube 强项。
> **选 Twine(SugarCube) 起步**；确需独特地图 / 界面，再退到**纯手写 HTML** 或用 **inkjs 内嵌方案**保证双击即玩。
> （Harlowe 格式更简单但脚本能力弱，复杂物品系统不如 SugarCube，故选 SugarCube 而非 Harlowe。）

## 4. 推荐技术方案（A / B / C）

### 方案 A：Twine（SugarCube 2）单 HTML —— ★首选

- **技术栈**：Twine 2 桌面版 / 在线版 + **SugarCube 2** 故事格式；`StoryInit` 集中初始化状态；`<<set>>` / `<<if>>` / `<<link>>` / `<<button>>` 控制流；SugarCube 内置 `State` / `memorize` / 自动存档 + 槽位存档；导出走 **Build → Publish to File** 得自包含单 HTML（资源用 base64 内嵌以保单文件）。
- **玩法骨架**：分支选项为主 + 轻状态栏（顶部固定显示 当前层级 / 杏仁水 / 隐藏理智用感官词替代显示）。每"层级" = 一个 passage 集群 + 一个 bottleneck 出口；层内若干 quest passage（地理探索）。理智隐藏，低于阈值时切换到"不可靠叙事"变体段落。
- **复用知识库的方式**：把 `后室/层级/*.md`（如 `Level-0-阈界（黄房间）.md`、生存难度 Class 0–5、畸变区"红房间/黑暗区/边缘移位"）转写为 passage 文案与环境表；`后室/实体/*.md`（Hound/Smiler/Skin-Stealer/Partygoer/Deathmoth…）转为"实体规避规则 + 错位线索"；`后室/物品/01-杏仁水`（灰/绿/红/蓝变体、每日三瓶、恢复约 50%）直接落为物品数据；`后室/组织/*.md`（MEG/UEC/TheLost…）做 NPC 阵营 / 结局走向。知识库即**世界圣经**。
- **工作量**：中等。引擎学习 1–2 天；机制脚手架（状态/物品/存档/状态栏）2–3 天；内容（每层级文案 + 分支）按层级数线性增长，建议首版做 L0→L1→L2→Level Fun + 2~3 个结局。
- **风险**：低。主要风险是**内容量**（IF 通病）与**外链资源破坏单文件**（用 base64 内嵌规避）；SugarCube 文档/中文教程充足，技术风险小。

### 方案 B：Ink + inkjs 内嵌单 HTML —— 剧情厚重型次选

- **技术栈**：用 **Inky** 写 `.ink`（线 / 编织 / 胶水 / 变量 / 函数），编译为 JSON；**inkjs** 运行时 + 自写极简 HTML 壳，把 JSON 字符串**内嵌**进 HTML（避开本地 file:// 的 CORS），导出单文件离线运行。
- **玩法骨架**：以**强叙事流**为主（Ink 的编织/胶水擅长细腻分叉与回合织文），适合把"先平庸后错位""循环 + 微小漂移"写得密。物品/状态栏 UI 需在 HTML 壳里手写（读 inkjs 变量渲染）。
- **复用知识库的方式**：同 A——层级/实体/物品/组织 md 作为世界圣经；Ink 的 `VAR` 管理理智/杏仁水/库存，`tunnel`/`thread` 复用通用片段（如"实体逼近"通用桥段）。
- **工作量**：偏高。Ink 语法上手 + 自搭壳 + 物品 UI 手写，比 A 多 2–4 天工程。
- **风险**：中。叙事能力天花板高，但**工程自造**多（壳 / 存档 / UI）；存档需自己用 inkjs 的 state save/load + localStorage 实现，易出 bug。适合"剧情厚、UI 简单"的取向。

### 方案 C：纯手写单文件 HTML + JS —— 机动 / 独特交互

- **技术栈**：单个 `.html`，内联 `<style>` + `<script>`；状态机 / 物品 / 分支 / 存档（localStorage 或可导出存档串）全自造；零依赖、天然单文件双击运行。
- **玩法骨架**：可做**打字指令 + 状态栏的存活流**（贴近 lemonlemon / Backrooms.Survive 范式：forward/left/look/pick up/use/read 指令 + 随机事件表），或任意独特地图/界面（如 ASCII 小地图、循环房间的"漂移"动画）。
- **复用知识库的方式**：把层级/实体/物品/组织 md 抽成 JS 数据对象（`levels[]` / `entities[]` / `items[]`），事件表引用之；最贴合"静态层 + 随机节点"的 roguelike 结构。
- **工作量**：中~高，取决于自造范围。无引擎学习成本，但状态/存档/分支全手写，**量大易乱**，需要良好的数据驱动设计。
- **风险**：中~高。100% 控制是优点也是风险——回归测试与防 bug 全靠自己；仅在"确需独特交互 / 做 demo"时优于 A。

### 首选推荐与理由

> **首选方案 A（Twine SugarCube 单 HTML）。**
> 理由：①需求"单文件双击 + 状态/物品/分支/多结局"被 SugarCube **开箱满足**，存档/库存/条件分支无需自造，直接规避了 2.3 中"存活系统常有 bug"的同类通病；②中文 UTF-8 无障碍 + 中文教程充足，Windows 本机零额外运行时；③后室题材"层级 = bottleneck 地图 + 物品/理智/逃脱条件"本质是状态机，正中 SugarCube 强项；④工作量/风险最低，能把精力压到内容与氛围（项目真正的胜负手）上。
> **回退路径**：若需独特地图/界面或更厚剧情织文，B（inkjs 内嵌）或 C（手写 HTML）作为退路，均能保住"双击即玩"。

## 5. 可落地的核心机制清单

### 5.1 状态变量

| 变量 | 类型 | 初值 | 规则 | 呈现 |
|---|---|---|---|---|
| `sanity` 理智 | 隐藏数值 0–100 | 100 | 每回合自然 -1~-3；黑暗/独处/目击错位事件额外扣；杏仁水/安全屋回升 | **隐藏，不显示数字**；用感官反馈表达（幻听、墙后低语、"熟悉的人声"、文字本身扭曲/重复、假实体） |
| `current_level` 当前层级 | 字符串 | `L0` | 跌层事件（no-clip）随机改变 | 状态栏显示层级名 |
| `turns` 回合/时间 | 整数 | 0 | 每个主选择 +1，驱动口渴/体力经济 | 可隐性 |
| `thirst`/`stamina` 口渴/体力 | 数值 | — | 杏仁水"每日三瓶"经济（3 瓶/天），不足触发衰弱 | 状态栏粗粒度（如"口渴/虚弱"标签） |
| `flags{}` 剧情旗标集 | 字典 | {} | 延迟后果用：记录早先选择，影响后续与结局（满足"延迟后果 + 状态追踪"） | 不显示 |
| `companion_trust` 同伴信任 | 数值（可选） | — | 替代多人 panic 传染：NPC 可靠性焦虑（剥皮者可能假扮同伴） | 不显示，靠对白透露 |

> 设计准则（Amnesia / Eternal Darkness 经验）：**理智用感官反馈而非数字**；让系统相互咬合（黑暗→理智↓，光源是消耗品）；别把氛围做成"游戏化"竞技。

### 5.2 物品（直接对接 `后室/物品/` 知识库）

| 物品 | 效果 | 副作用 / 限制 | 来源条目 |
|---|---|---|---|

> 物品 = 多变体消耗品 + 资源经济。**忌做成无限补给**——稀缺性是恐惧来源之一。

### 5.3 分支结构（Sam Ashwell《Standard Patterns》骨架）

| 骨架 | 特性 | 在本项目的用途 |
|---|---|---|
| **Branch-and-Bottleneck** | 分支定期汇合 + 状态追踪，适合角色成长 | **主干**：每"层级"末尾是一个 bottleneck 汇合点 |
| **Quest** | 按地理分模块，适合探索 | **层内**：每层 = 若干地理 quest 模块 |
| **Gauntlet** | 线性主线 + 死亡剪枝，最易编写，契合危险世界 | 危险层级（如 Level !）用 Gauntlet 制造高致死走廊 |
| **Time Cave** | 强分支多结局，高重玩但内容易错过 | 局部高潮 / 结局收束段 |
| **Open Map / Loop-and-Grow** | 适合循环 / 沙盒 | 表达"循环 + 微小漂移"的迷路层（如红房间死循环） |

> **推荐主干 = Branch-and-Bottleneck + Quest 混合**：层级即天然 bottleneck 地图，层内地理探索。
> **避免无意义选项**：每个选择须有可见后果（叙事/世界/数值）；用**延迟后果 + 状态追踪**；砍二元善恶，做**道德灰色两难**；选项前用线索预示后果；质量 > 数量；**忌"不同选项同结局"**。

### 5.4 多结局

- 至少 4–8 个结局（参照《Backrooms: Choices》8 结局），由 `flags{}` + 关键状态（理智/物品/同伴信任/所在层级）共同决定。
- 结局类型示例：**逃出后室**（真结局，需集齐条件）/ **困死 L0**（资源耗尽，对应 85% 走不出 L0 的设定）/ **理智归零→成为后室一部分**（不可靠叙事终点）/ **被实体同化 / 被剥皮者取代** / **加入某组织**（MEG/UEC/TheLost，对接 `后室/组织/`）/ **永坠循环**（红房间/边缘移位）。
- **节奏**：恐怖靠张弛交替——安全屋/低强度 ↔ 突发危险；延迟解释、保留未知（实体规则不全公开）维持 dread。

### 5.5 存档

- **存档点设在安全房间**（每层级的 bottleneck / 安全屋），对接 SugarCube 自动存档 + 手动槽位存档。
- 借 roguelike：**静态层 + 随机节点**——层级布局固定但层内事件/掉落/实体遭遇随机，提升重玩性。
- no-clip = **随机跌层事件**（小概率把玩家甩到非预期层级），既是机制也是叙事张力来源。
- 实体分层规避（对接 `后室/实体/`）：不同层不同实体、不同生存规则——0 层 Hounds / 1 层 Smilers·剥皮者 / Fun 层派对客，错套规则即死亡。

## 6. 落地建议（执行顺序）

1. **搭骨架**：Twine + SugarCube，建 `StoryInit`（5.1 状态）、物品系统（5.2）、状态栏组件、存档点。
2. **跑通最小闭环**：L0 → L1 一条主线 + 1 个死亡结局 + 1 个推进结局，验证理智隐藏反馈与杏仁水经济手感。
3. **接知识库**：把 `后室/层级`、`后室/实体`、`后室/物品`、`后室/组织` 内容转写为 passage / 数据，作为世界圣经，保证 lore 自洽防漂移。
4. **铺内容**：按 Branch-and-Bottleneck + Quest 扩到 4–8 层 + 4–8 结局；每个选择过"是否有可见后果"检查。
5. **氛围打磨**：第二人称现在时、先平庸后错位、感官极简、严控 jumpscare；理智低段写不可靠叙事变体。
6. **导出验收**：Publish to File → 单 HTML，base64 内嵌资源，双击 Windows 本机验证可玩、存档、多结局可达。
